# GGUF matvec 优化实验报告

日期：2026-11-08。环境：Eureka，RTX 5080 16GB，Qwen3.8-27B UD-IQ3_S GGUF，vLLM 源码分支 feat/dynamic-vision-cache，单并发、FP8 KV、关闭前缀缓存、prefill 分块 1024。

## 结论

最终启用 matvec 输出免清零，生成速度由约 46.5 提高到约 50 token/s。线程块、每块输出行数和 IQ 数据读取候选未取得稳定端到端收益，保持关闭。没有改变量化权重、数学运算和默认线程块布局。

## 重新确认热点

复制消除后的短文本 decode GPU trace 中，GGUF matvec 占归属到 decode 区间的 kernel 累计时间约 89.6%（438.11 / 488.81 ms）。这是 kernel 时间归因，不是整个请求的耗时占比。最终性能测试关闭 profiler，以免采集开销影响结果。

## 实验过程

1. 扫描每块输出行数 1、2、4、8、16，覆盖实际线性层形状及 LM head，逐类型检查。部分 K 类量化形状在微基准中获益，但端到端收益不稳定。
2. 对 IQ3_S、IQ3_XXS、IQ4_XS 尝试打包读取和循环展开。热缓存微基准的改善没有转化为稳定生成加速；256 MiB 缓存冲刷对照也不支持显著改善。未采集 DRAM/L2 硬件计数器，因此不据此断言已达到带宽极限。
3. 将候选选择移到 C++ 原始算子，排除 Python 分派开销。线程块与读取候选仍没有稳定收益，不默认开启。
4. 检查 matvec 内核：每个有效输出元素均由对应线程直接赋值，旧输出值不参与计算。因此将输出分配从 new_zeros 改为 new_empty，删除一次多余初始化及其执行开销。最终 mode=3 仍使用基准数学和一行/warp 布局。

## 端到端结果

同一进程切换基准 mode=0 与优化 mode=3，每种场景先预热，再各测 3 次，固定生成 128 tokens，表中为中位数。decode 速度根据首个至最后一个生成 token 的时间计算，区别于包含 prefill 的端到端速度。

| 场景 | 基准 decode token/s | 优化 decode token/s | 提升 | 基准/优化 TTFT |
|---|---:|---:|---:|---:|
| 短文本，43 输入 tokens | 46.56 | 49.94 | 7.3% | 0.184 / 0.180 s |
| 长文本，15,020 输入 tokens | 46.57 | 50.04 | 7.5% | 13.856 / 13.875 s |
| 图片，606 输入 tokens | 46.46 | 49.91 | 7.4% | 0.829 / 0.798 s |

长文本 TTFT 基本不变，符合本次修改主要作用于 decode 的预期。三个场景的进程显存峰值分别约 14.09、14.73、14.18 GiB，基准与优化一致。

额外交替 A/B/A/B 测试：每次生成 256 tokens，每种模式 6 个样本。基准中位数 46.48 token/s（46.25–46.72），优化 49.70 token/s（49.56–49.82），提升 6.9%。这组结果用于交叉确认，而非替代上述场景测试。

## 正确性与服务回归

- 最终免清零路径：54 个实际线性层形状、14 种量化类型、380 个测试，逐字节一致。
- 覆盖 BF16 实际形状、F16/F32 代表形状、多输入向量、尾行及 NaN 污染的分配器内存，防止依赖未初始化内容。
- 文字、图片、取消请求、排队准入与预算锁定回归通过。
- 服务重启后文字回答“巴黎”，图片识别“红色”；健康接口返回 200。
- 图片请求结束后 cache_bytes=0、blocks=0，视觉权重回到 CPU。
- 本轮验证不等于完整模型质量评测；线程块和读取试验没有作为默认配置启用。
